# SC試験対策 — 情報処理安全確保支援士 午前I / 午前II / 午後

情報処理安全確保支援士試験（SC）の過去問19回分を、手元のPDFから抽出して学習アプリで
使える形にするためのリポジトリ。**午前I（高度共通・30問50分）・午前II（25問40分）・
午後（記述式）**の3区分を扱う。

午後は令和5年度秋期に **午後I（90分・3問中2問）と午後II（120分・2問中1問）が
午後（150分・4問中2問）に統合**された。アプリ上は1つの区分としてまとめ、大問ごとに
どちらの試験のものかを持たせている。

> **著作権について。** 抽出元のうち IPA の問題冊子と翔泳社『情報処理教科書 安全確保
> 支援士』読者特典の解説は、いずれも著作物。`data/` 以下（`questions.json`・
> `figures/`・`build/`）は**公開リポジトリ・公開URL・公開ストレージに置かない**。
> `.gitignore` でも除外している。

---

## 1. 必要なもの

| | |
|---|---|
| macOS | PDFKit と Vision を使うため必須。Apple Silicon / Intel どちらでも可 |
| Xcode Command Line Tools | `xcode-select --install`（`swiftc` が要る） |
| Python | 3.9 以上。macOS 標準の `/usr/bin/python3` でよい（追加パッケージ不要） |
| tesseract | **任意**。あると OCR のクロスチェックが有効になり、要確認リストの精度が上がる。`brew install tesseract tesseract-lang` |

Homebrew の poppler（`pdftotext` / `pdfimages`）は**不要**。理由は §5 を参照。

既定では `~/Desktop/情報セキュリティSP過去問/` を見に行く。別の場所なら環境変数で指定する。

```bash
export SC_PDF_ROOT=/path/to/情報セキュリティSP過去問
```

## 3. 実行

```bash
./tools/run_all.sh                  # 午前I・午前II・午後 の全19回
./tools/run_all.sh --section am1    # 午前Iだけ
./tools/run_all.sh --section pm     # 午後だけ
./tools/run_all.sh R07aki           # 全区分の R07aki だけ
```

各ステージは `--section am1|am2` を受け取り、中間生成物は `data/build/<区分>/` に
分かれる。統合（`06_build`）以降は両区分を1つの `questions.json` にまとめ、各問に
`section` を持たせる。

各ステージは単体でも動く。冪等なので何度流し直してもよい。

午前（01〜05）と午後（11〜15）で前段が分かれ、`06_build` で1つに統合する。

## 5. 設計上の判断

**PDFの読み取りに poppler ではなく PDFKit を使っている。** この環境に poppler が
入っておらず、また `pdftotext -layout` よりも PDFKit のリーディング順のほうが解答例
PDFの3段組を正しく1行1件で返した。macOS 標準フレームワークだけで完結するので、
数年後に再実行しても壊れにくい。実体は `tools/swift/pdfkit-tool.swift`（`bin/pdfkit-tool`
に自動ビルドされる）。

**OCR は Vision を採用した。** 同一ページで tesseract と比較した結果:

| 指標 | Vision | tesseract |
|---|---|---|
| 問N見出しの認識 | 24/25 | 14/25 |
| 行頭の選択肢マーカー | **100/100** | 77/100 |
| 全角括弧・全角読点の保持 | 保持する | すべて半角化 |
| 1ページあたり | 約0.6秒 | 約1.5秒 |

選択肢マーカーの取りこぼしは構造の破壊に直結するため、この差は決定的。ただし
tesseract のほうが正しく読む字もある（`危殆化` など）ので、**入れてあれば第2エンジン
として突き合わせに使い**、両者が食い違った文字を要確認リストに載せる。

**午後は「解答から問題文へ」逆向きに組んでいる。** 問題冊子はスキャンでOCRが要るが、
解答例・採点講評・教科書解説の3つは**すべてテキスト層がある**。そこで、まず解答例PDF
（表形式で「設問1 / (1) / 空欄a / 解答」が読み取れる）から**設問の骨格を作り**、その
記号をOCRした問題文の中から探す。散文を白紙から構造化するより桁違いに堅い。全838設問
のうち**設問文が取れたのは838件**。

**午後の空欄は「隙間」から見つけている。** 空欄の枠線は図形なので、OCRには枠も中の
記号も写らないことが多い。代わりに、同じ行の断片どうしの**横の隙間が字送りでは説明
できない幅**なら、そこに枠があったとみなす（`［　］`）。記号が読めていればそれを入れる
（`［a］`）。読めていない記号を解答例から推測して埋めることはしない。

**ただし隙間の大半は空欄ではない。** 表の列の区切りも図の配置も同じ隙間になる。素直に
拾うと6,865個の空の枠が並び（記号入りは849個）、「本文中の［ ］」がどれを指すのか
分からなくなる。そこで3つで削る:

1. **縦に揃う隙間は列の罫線。** 同じページで3行以上が同じx位置に隙間を持てば、それは
   表の列であって空欄ではない
2. **1行に空の枠が2つ以上あれば配置の隙間。** 設問は空欄を1つずつ指すので、
   `サーバ［ ］サーバ［ ］サーバ` は図の中の並びであって埋める場所ではない

3. **紙にインクが乗っているか。** 空欄は印刷された枠なので、そこには必ず何かが
   刷られている。列の隙間も図の余白も白紙。`bin/pdfkit-tool ink` がページを描画して
   各隙間の黒画素率を返し、0.02未満なら枠ではないとみなす。しきい値は 2026-09-04 に
   記号が読めた枠758個で較正した（落ちるのは12個だけで、それも矩形の取り違えに見える）

結果、本文の空の枠は **6,865個 → 886個**。設問文側は触らない。

**枠の中の記号は、枠だけを切り出して読み直す。** 記号は枠の中に本文の半分ほどの
大きさで組まれていて、ページ全体の一部として読むと落ちるほうが多い。そこで、枠の
矩形だけを400dpiではなく600dpiで描画し、1枠ずつ Vision にかける（`pdfkit-tool
rectocr`）。読み取り結果は最大3候補まで返し、**その大問の解答例が挙げているラベルに
一致するものがちょうど1つのときだけ**採用する。0個でも2個でも枠は空のままにする。

**隙間が1つの枠とはかぎらない。** 「［f］は［g］しておく」のように、枠と枠のあいだの
文字までまとめて落ちると、隙間ひとつに枠が2つ入る。そこで rectocr は矩形の中で
見つけた文字の並びを**1かたまりずつ**返し、かたまりごとにラベルを当てる。ラベルに
ならなかったかたまり（上の例の「は」）は捨てる。読み取れた文字をそのまま本文に
入れると、本物の文字と誤読が混ざるため。

較正は、ページ読みで記号が取れていた849個を正解として行った。**採用したときの正確さ
97%、正解の78%を復元**。枠の上下の取り方を変えて3回読み、同じ位置のかたまりの候補を
合わせている（`FRAME_CROPS`）。1回だけなら復元は63%に落ちる。第1候補を無条件に採る、
1 を l と読み替えるなど緩めた規則も測ったが、いずれも正確さが93〜96%に落ちるので
採らない。

**行頭と行末の枠は、隙間ではなく行の形で見つける。** 行の先頭にある枠には前に断片が
無く、行末の枠には後ろに断片が無いので、どちらも隙間としては現れない。代わりに:

- **行頭**: その行が上の行より内側から始まっていれば、左から押さえているのは枠
- **行末**: 日本語は行末までびっしり組むので、段落の途中なのに行末が余っていれば、
  右で止めているのは枠。ただし散文の行だけ（表の行や図のラベルはセルの都合で
  止まる）で、句点や英単語で終わる行も除く

中央寄せの行（キャプション、ページ番号）と、見出しや小問や問Nを開く行は除く。こうして
見つけた枠は「見えた」のではなく「推した」ものなので、**記号がちょうど1つ読めたとき
だけ**空欄にする。読めなければ何も置かない。

結果、記号の読めた枠は **589個 → 983個**。

**記号が枠の外に出ることがある。** 「［d］の対策と併せて」が「d［ ］の対策と併せて」に
なる。ページ読みが記号を前の断片の末尾として拾うと、枠は空のまま残る。枠の隣にある
1文字がその大問のラベルなら、枠の中に戻す（91件）。ただし**ハイフンやカタカナの後ろは
除く**。`SaaS-a`・`DNS-K`・`サイトA` は固有名詞で、末尾の文字は空欄記号ではない。

**それでも読めない記号は、前後のラベルから置く。** IPAは大問の空欄を a, b, c… と
本文の順に振るので、設問が問うているのに一度も出てこない空欄は、前後の空欄に挟まれて
いる。最後の ［k］ より後、最初の ［n］ より前に残っている空の枠が、その区間で欠けて
いるラベルを頭から順に取る。

推測なので、囲いを厳しくしてある。1文字のラベルだけ、設問が「本文中の」と言っている
ものだけ、散文の行の枠だけ（表の中の枠は画像に差し替わっているし、その設問は「表2中
の」と書く）、そして**枠の左右のどちらかが平仮名か読点であること**。名詞と名詞に
挟まれた枠は、行が散文に見えても表の列の隙間か図の余白で、この条件で落ちる。角括弧が
本文そのものである場合（`char *argv［］`）は、括弧の前が英数字なので外れる。7件。

**枠が丸ごと落ちて、記号だけが残ることもある。** 「表2の［a］行目が［b］脆弱性を
狙った」の ［b］ は、罫線が写らず素の `b` が助詞のあいだに立っていた。まだ見つかって
いないラベルが事例のどこかにちょうど1回だけ、そうして立っているなら、それを枠にする。
丸数字は下線の印なので除く。1件。

**行ごと落ちていることもある。** 令7秋 問1 の ［j］ は「・SAST」と並ぶ箇条書きの
2つ目で、**その1行だけ**がスキャンに写っていなかった。置くべき枠が無いので、前後の
ラベルからも置けない。そこで**行間の広さで探す**。本文は等間隔に組まれているから、
ページごとに行送りの中央値を測り、**その2.5倍以上あいている場所**がその区間に
ちょうど1つ、欠けているラベルもちょうど1つのときだけ、そこに ［j］ だけの行を作る。
ページ番号の行と紙の下端（y>0.88）は除く。記号を推して読んでいるのではなく、
**一行あったことだけを書いている**。1件。

**数字と読まれた記号は、その事例に無いラベルにだけ折り返す。** 枠の中の文字は本文の
半分の大きさで組まれていて、200dpi では `1`/`l`/`i`、`9`/`g`、`6`/`b`、`0`/`o`、
`5`/`s` が同じ数ピクセルになる。一律に読み替えると正確さが 97%→96% に落ちるので
（2026-09-06 に測って却下した）、次の3つを全部満たすときだけにした。

- そのラベルが**その事例のどこにも出てきていない**（取り違え以外に説明が付かない）
- 数字が**第1候補**であること（`['j','6','5']` のように文字が先に来るものは対象外）
- 当てはまる文字が**ちょうど1つ**（`1` は `l` にも `i` にも化けるので、大問がどちらか
  一方だけを使っているときに限る）

令7春 問2 の ［l］ がこれ。「［l］を継続的に行うことで被害を防ぐ助けになるだろう。」

**行頭の枠が2つ並ぶことがある。** 令7春 問2 は「，［f］や［g］だった。」と組まれていて、
スキャンが行頭から「や」まで丸ごと落としている。行が右にずれて始まることで枠としては
見つかり、600dpiで読み直すと `[['f'], ['や'], ['9','g']]` と正しく取れているのに、
「ラベルがちょうど1つのときだけ採用する」規則で捨てていた。この規則は「行頭の枠は位置
から推した推測なので、2つ読めたのは隣の本文を巻き込んだ証拠」という意味だった。

そこで、**ラベルが互いに異なり、矩形の中の断片が4つ以下で、ラベル以外の断片がすべて
2文字以下**のときだけ、まとめて採る。隣の本文を巻き込んだ場合はラベル以外の断片が
単語の長さになるので落ちる。この冊子では行頭の枠80個のうち該当は1個だった。

**行末の枠は、その行に別の枠があっても探す。** 行末の枠は後ろに断片が無いので隙間として
現れず、行が右端まで届いていないことで見つける。最初はこの規則を「枠がゼロの行」に
限っていたが、平30春 午後I 問1 は「アドレス［c］番地に値［d］を」と組まれていて、
スキャンが ［d］ から先を落としている。行は ［c］ を持つので対象外になっていた。
除くべきは**表の列の罫線**だけ（表のセルは終わるところで終わる）なので、そちらに直した。
記号の読めた枠が7個増えた。

**ページ番号は本文でも設問文でもない。** 紙の下端に `- 12 -` が独立した行として刷られて
いて、ページをまたぐ設問はそれを末尾に連れてくる（「70字以内で述べよ。 - 12 =」）。
落とすときは**罫線状の記号が数字に接していること**を条件にする。裸の数字は字数や項番
だし、解答群の選択肢「ケ SHA-512」はハイフンの後ろに数字が来る。設問文114件と
本文257行を落とした（`tools/06_build.py` の `pm_drop_page_no`）。罫線状の記号は
`－`(U+FF0D) まで含め、末尾に句点が付く形（`27-.`）も見る。残るのは `SHA-512`
`X.509` `9.~10.` `1=1` のような、数字を含むが罫線を伴わないものだけ。

**最後まで規則で届かなかった空欄は、ページを見て置いた。** 「本文中の」と言われている
のに本文に無い空欄が25個残ったところで、一般則は立たなくなった（置くべき区間に空の枠が
ちょうど1つあるのは25個中2個だけ、13個は枠そのものが検出されておらず、6個は候補が3つ
以上あって決められない）。そこで**1件ずつページ画像を読んで**、事例ごとの文字列置換として
`tools/pm_blanks.json` に書いた（26件）。内訳は、枠ごと落ちていたもの、行頭・行末で
切れていたもの、記号が枠の外に出ていたもの、そして**枠の中の記号を別の文字と読んで
いたもの**（`1`→`i`、`b`→`q`、`a`→`α`、`を`→`く`、`は`→`f`）。

`find` は事例の中でちょうど1回現れることを 06_build が検査する。抽出が変わって当たら
なくなった修正は `data/build/review.md` に出るので、黙って消えることはない。

**設問文の空欄は、解答例が正。** 設問文の側は隙間の取りこぼしがそのまま出るので、
解答例のラベルと突き合わせて直す。枠の数がラベルの数と揃えば1つずつラベルを与え、
記号のある枠だけでラベルが出そろっていれば余った空枠を落とす。ほかに4つ:

- **枠の右罫線が二度写る。** 「［b］，［c］に入れる」が「［b］［c］】に入れる」。84件。
  本物の鉤括弧（イベントログの「［f］」）は行の前に開き括弧があるので見分けが付く
- **枠が letter を挟んで二つに割れる。** 「［l］に入れる」が「［ ］1［ ］に入れる」。
  記号が枠の外に出ると隙間が左右にできる
- **範囲の左端が閉じ罫線だけになる。** 「［e］～［g］」が「」～［ ］」。左側は括弧に
  限る。英字まで許すと解答群のMACアドレス `XX-XX-XX-…` を範囲と読む
- **ラベルが1つで枠も1つなら、枠の中が何と読めていようと解答例が正。** 207件のうち
  3件が食い違っていた
- **記号が枠の外に出る**（「ア［ ］」→「［ア］」）、**枠ごと消えて記号だけ残る**
  （「本文中のc に入れる」→「本文中の［c］に入れる」）。設問のラベルは2〜4個しか
  ないので、事例の側と違ってカタカナも対象にできる
- **枠が2つ並んでいて解答例のラベルが3つ以上なら範囲。** IPAは2つなら並べて、3つ
  以上なら「［a］～［e］」と書く。あいだの波線は図形なので、残る回数と同じくらい
  落ちる。ただし**ラベルは1種類の記号でそろっていること**を条件にする（a…z か
  あ…こ か ア…ン か α…ω か ①…⑳）。解答例の表の行見出し（「作成時」「必要な
  全てのコード」）や、記入例の番号 ① が混ざっているものは空欄ではない

これで**設問文の枠がラベルと完全に一致するのは 296/428**。残りは範囲表記
（「［a］～［e］」の2枠に対しラベルは5つ）が大半。

**それでも、記号が読めていない枠は「ただの隙間」と完全には区別できない。** 幅でも
枠線の形でも設問からの逆算でも分離しなかった（`STATUS.md` に測定結果）。そこで
アプリ側では**記号のある枠だけを強調し、空の枠は素のまま出す**。全部を強調すると、
正しい空欄より誤ったものを指し示す回数のほうが多くなる。

**記号があっても空欄とはかぎらない。** 本文が本当に角括弧を刷っている場合がある。
`argv［1］` はコードの添字だし、`［チョコ］` は検索語、`［を］` は行から切り出された
助詞。記号のある枠983個のうち133個がこれだった。そこで事例に `blanks`（その大問の
解答例が挙げるラベル）を持たせ、**アプリはそこにある記号の枠だけを空欄として扱う**。

**9冊は「上余白ごと切れたスキャン」に見えていたが、こちらの描画の誤りだった。**
（H28春・H28秋・H30秋・R01秋の午後I・午後II、R03秋の午後I）これらのPDFのページは
`/Rotate 90`（または270）を持つ。PDFKit の `bounds(for:)` は**回転を適用する前**の
枠を返すのに `draw(with:to:)` は**回転を適用して**描く。枠に合わせた横長の画布に
縦長の紙が描かれるので、**紙の上から約3割が画布の外に落ちていた**。1ページあたり
10行ほど、大問の見出し `問1 …に関する次の記述を読んで` の行も、設問文も消えていた。
`displayBox()` で回転時に縦横を入れ替えて解消（設問文 778件 → 837件、図表 +41枚）。
午後の問題冊子19回分のうち13冊が `/Rotate` を持ち、うち9冊が四分の一回転。180度は
縦横が変わらないので影響がない。午前は R03秋 午前Iの180度だけで、影響はない。

これに伴い、切れたスキャン向けの回避策を2つ落とした。大問の境界を設問行のかたまりから
求める `split_by_setsu` と、切れた `設問1` の行の上に残った小問を拾う `widen_cut`。
どちらも一度も動かなくなり、後者はむしろ事例の表と段落を設問側へ引き込んでいた。

**午後の図表はキャプションの位置から切り出す。** 日本語組版では**表のキャプションは上、
図のキャプションは下**に置く。表はキャプションから下へ、図はキャプションから上へ、
本文の段落に当たるまでを1枚として切る。図の側は「取りこぼすより広めに取る」判断にして
あり、図の上に導入文が1行入ることがある。設問が参照している図の一部が欠けるほうが実害が
大きい。キャプションのある図表777枚を切り出せている。図表がページの先頭にあり
キャプションが下にある場合に取りこぼしていたが、段落をページ境界で連結しないよう
にして解消した（+31枚）。

**図の中の文字は、本文に二度出さない。** 切り出した絵を出すのだから、その絵から読んだ
OCRの断片を横に並べれば同じことを二度書くことになる。しかも断片は読み順に潰れていて、
`a を送` `→` `（5） 9` のように読めない（令7春 問3 の 図9 がまさにこれだった）。
**キャプションは中央寄せとはかぎらない。** 長いキャプションは行末近くまで届くので
「左右から引っ込んでいる」判定では拾えず、12件が散文として扱われ、切り出されずにいた
（令1秋 問1 の 図4 など）。散文は図番号の直後に助詞が来るが（「図1の設定では」
「表4に基づいて」「図3中の6について」）、キャプションはそのまま名詞に入る
（「図1 クラウドサービス利用に関する…」）。この違いで候補29件が12件のキャプションと
17件の散文にきれいに分かれた。図表 762→777枚、設問からの図表リンクは **471/471**。

**絵に入らなかった断片は、本文と同じ組み方で出す。** 以前は等幅・字下げの `figtext` で
出していたが、段落の途中に字下げが現れるのは組版の誤りにしか見えず、読み手にできることも
無い。1,428行あったそれを 0 にした。

そこでキャプションから歩いて、絵に置き換える行を印にする（`drawn`）。決めるのは3つ。

- **キャプションの向きに歩く。** 表のキャプションは表の上、図のキャプションは図の下。
  逆向きに歩くと、図を導入する文のほうを飲み込む
- **絵の矩形の中にあること。** 切り出しに入っていない行を隠すと、絵にも本文にも無くなる。
  この条件を入れる前は141行がそうなっていた
- **走査が届かなくても、矩形の中にあって散文の書かれ方でない行は絵の中身。** 連なりは
  改ページや散文として組まれた注記で切れる
- **散文に見える行を1行だけ飛び越す。** 表のセルを読み順に潰した行は散文と見分けが
  付かない（「フェーズ32さんとB社での診断A 社グループである…」）。2行続いたら終わりに
  するので、図を導入する文は飲み込まれない

2,262行がこれで絵になり、**絵に写っていない行を隠すことは無くなった（141→0）**。

**どこから始まる行かでは決められない。** 最初はこれを左端の位置で判定していて、事例の
本文を丸ごと消した。平30春 午後I 問1 は余白を3つ持つ — C++のリストが 0.115、段落が
0.15、会話文の折り返し（「T主任：」の下がり）が 0.23 — そして `base_indent` は
「いちばん多い左端」を返すので 0.23 を選ぶ。段落も会話文も「余白ではない」と判定され、
155行のうち140行が図の中身として絵に置き換わった。corpus 全体では本文の48%が消えていた。

**代わりに、行の書かれ方で判定する。** 図のラベルはセルの隙間を持ったまま返ってくる
（`関数テーブル メイン処理 共有ライブラリ`）が、日本語の散文はベタ組みで、空白は英単語の
周りにしか無い。**語中に空白が無く、文と言える長さの日本語がある行**を散文とする
（`looks_prose`）。組み方に依存しないので、余白がいくつあっても効く。絵に置き換わる行は
6,887 → 6,660（本文の47%）になった。図表の枚数は777枚。

**表は、文章に見えるセルも含めて全部隠す。** 表のキャプションは表の上にあり、切り出しの
走査は表の下の最初の散文で止まるので、**矩形の中は全部セル**である。セルを読み順に並べると
読めない — 「機器名 ［ ］ 概要 / 内部 DNS・DNS コンテンツ機能 / サーバ ［ ］ - 社内専用の
ドメイン名を管理する。」 — ので、1つのセルが文らしく見えても落とす。図はキャプションが下に
あって矩形が導入文の上まで伸びるので、そちらは書かれ方で決めるまま。

**その図が持っていた空欄記号と丸数字は、絵が引き継ぐ。** 隠した行に ［e］ があれば
絵に `data-blanks` として持たせるので、設問の「図9中の［a］」は絵まで飛ぶ。読み手が
見に行きたいのはどのみち絵のほうで、記号は絵の中に刷られている。

**図の高さの上限は測り直した。** 図はキャプションから上へ、前のキャプション・見出し・
ページ先頭まで歩くが、際限なく歩かないよう高さで止めている。この上限が 0.62 では
足りず、令7春 問3 の 図9（紙の0.65）は**自分のレーン見出しごと切り落とされて**いた。
切り落とされた行は絵に入らないので本文に残り、絵と本文に半分ずつ散る。0.70 にした。

**誤認識の検出に解説テキストを辞書として使っている。** 教科書解説PDFはテキスト層が
あり、OCRを通していない約13万字のきれいな同分野コーパスになる。OCRした問題文に
「解説側に一度も現れない漢字」があり、かつ tesseract もその字を読んでいなければ、
ほぼ誤読（`擎`←`撃`、`億`←`偽` など実例あり）。

**読点は「，」に戻す。** IPA は読点を全角カンマで組むが、Vision はその多くを「、」と
読む。決め手は同じ冊子の**解答例と採点講評にテキスト層がある**ことで、そこには
「，」が1,604回・「、」が**0回**。tesseract も独立にカンマとして読む。午前は
`tools/04_parse.py` の `norm()` で以前からこれを直していて、午後だけ引き継がれて
いなかった（`tools/14_pm_parse.py` の `PUNCT`、14,110箇所）。教科書解説は翔泳社の
テキスト層で本当に両方を混ぜて使っているので、そちらは触らない。

**カタカナ語は、その事例自身の数え方で直す。** 事例は同じ語を何度も刷る（平30秋
午後II 問1 の「サーバ」は132回）。だから**その事例に1度だけ現れて、同じ事例の多い語と
1文字しか違わないカタカナ語**は、その語の読み違いであって別の語ではない。`サーノ`
`サニバ` `リーバ` `ナーバ` はすべて `サーバ`。19語を直した。

危ないのは逆側で、`化学メーカ`・`DNS シンクホール`・`キーボード入力` はどれも
多い語と1文字違いだが実在する。4つの条件で外している:

1. 事例内で少数派が2回以下、多数派が10倍以上
2. 午後全体でも5回以下（実在語は19回にまたがって出る。誤読は一度きり）
3. **テキスト層60万字の辞書に無い。** 教科書解説（午前＋午後）＋ IPAの解答例 ＋
   採点講評。どれもOCRを通していないので綴りは定義上正しい。メーカ・ホール・
   ボードはここで落ちる
4. 候補が2つある語は保留。`ホール` は `メール` とも `ツール` とも1文字違いで、
   事例がどちらとも言っていない

`tools/06_build.py` の `pm_vote_terms`。

`data/questions.json` のスキーマは `schemaVersion: 1`。午前は1問=1レコード。

```jsonc
{
  "id": "R07aki-am2-01",
  "sessionId": "R07aki",
  "section": "am2",
  "no": 1,
  "text": "…",
  "choices": [{ "key": "ア", "text": "…" }, …],
  "answer": "ウ",
  "explanation": "…",
  "explanationSource": "情報処理教科書 安全確保支援士 読者特典",
  "figures": ["figures/R07aki/R07aki-am2-22.png"],
  "choiceFigures": {},
  "tags": ["暗号"],
  "duplicateGroupId": null,
  "needsReview": false,
  "shortText": true,
  "source": { "questionPdf": "…", "page": 3, "pageImage": "…" }

```

**午後は2種類。** 事例（`cases`）が本文と図表を持ち、設問（`questions`）がそれを指す。
設問を平らなまま `questions` に置いているので、ライトナーの箱も学習記録も統計も午前と
同じコードがそのまま動く。**解き直したいのは10ページの事例ではなく、間違えた設問**
だからでもある。

```jsonc
// cases[]
{
  "id": "R07aki-pm-1",
  "sessionId": "R07aki", "section": "pm", "paper": "pm", "no": 1,
  "title": "コンサルティング業務で利用する SaaS",   // 教科書解説から
  "intent": "…",            // 解答例PDFの「出題趣旨」
  "overview": "…",          // 採点講評の全体講評
  "overviewRate": "平均",   // 高 / やや高 / 平均 / やや低 / 低
  "body": [{ "kind": "para|heading|caption|figure", "text": "…", "page": 2 }],
  "figures": [{ "label": "図1", "caption": "…", "page": 4, "file": "figures/…png" }],
  "pages": [2, 7],
  "tags": ["Webセキュリティ"]
}

// questions[]（午後）
{
  "id": "R07aki-pm-1-2-3",
  "sessionId": "R07aki", "section": "pm", "caseId": "R07aki-pm-1",
  "no": 103,                       // 事例内の通し番号（並べ替え用）
  "setsu": 2, "sub": 3, "label": "設問2(3)",
  "text": "図4中の［　］に入れる適切な文字列を、図2から抜き出して答えよ。",
  "lead": "〔インシデントの発生とその調査〕について答えよ。",
  "answerKind": "choice|term|essay",
  "parts": [{ "label": "d", "answer": "…", "options": [], "kind": "essay" }],
  "remarks": ["順不同"],
  "explanation": "…",              // 教科書解説（設問単位）
  "commentary": "…",               // 採点講評（設問単位）
  "commentaryRate": "低",
  "tags": ["Webセキュリティ"],
  "needsReview": false

```

`parts` が空欄ごとに分かれているのは、**半分だけ合っている解答を △ にできる**ように

| kind | 例 | 採点 |
|---|---|---|
| `choice` | `ウ，エ` / `b ウ` | 正規化して完全一致で自動判定 |
| `term` | `ロール管理` / `メッセージ認証符号` | 同上。外れたら自己採点に落とす |
| `essay` | `出力時にエスケープ処理を施す。` | 自己採点のみ（○/△/×） |

全19回838設問の内訳は **記号選択 113 / 語句 308 / 記述 417**。記号と語句を合わせた
424件（50.5%）は自動で採点でき、残りの記述は解答例・採点講評・解説を並べた上で
自分で ○ / △ / × を付ける。

## 7. Webアプリ

`app/` がアプリ本体。ビルド工程はなく、HTML + CSS + ES modules だけで動く。

### 公開先

**https://aoe99.github.io/sc-am2-study/app/**（アプリ名: SC試験対策）

Service Worker がアプリ本体（21ファイル）をキャッシュするので、一度開けば
オフラインで動く。iPhone は共有 →「ホーム画面に追加」。

### ローカルで動かす

```bash
python3 tools/serve.py        # → http://localhost:8765/
```

または `起動.command` をダブルクリック。インターネットは不要
（127.0.0.1 にしか listen しない）。

初回に「ファイルを選ぶ」から `data/sc-data-am.json`（午前Ⅰ・午前Ⅱ）と
`data/sc-data-pm.json`（午後）を読み込む。以降は IndexedDB から読むので、
オフラインでも動く。

### なぜ区分ごとに分けるのか

午前だけで既に18MB・図表566枚ある。午後の879ページ分をここに足すと、iPhone の Safari が
一度にメモリへ読み込めない。そこで**パックは区分ごとに分け、アプリは読み込んだパックが
名乗った区分だけを差し替える**。午後を入れても午前1,045問と学習記録はそのまま残る。

### なぜ「ファイルを選ぶ」なのか

問題文も解説も著作物なので、**アプリと一緒に配信しない**。`app/` だけなら
GitHub Pages などの HTTPS に置ける（Service Worker は HTTPS か localhost でしか
動かないため、iPhone で PWA として使うには HTTPS 配信が要る）。問題データは
利用者が自分の手元のファイルから読み込む。`.gitignore` で `data/` を除外済み。

### iPhone

1. `data/sc-data-am.json` と `data/sc-data-pm.json` を iCloud Drive に置く
2. Safari でアプリを開き、「ファイルを選ぶ」から**それぞれ**読み込む（順不同）
3. 共有 →「ホーム画面に追加」

Safari の「サイトデータを消去」で学習記録が消えるので、設定画面から
**書き出し**ておくこと。同期機能ではなく手動バックアップ。

### モード

| | 午前 | 午後 |
|---|---|---|
| 練習 | 出題数・年度・分野・未着手/誤答で絞る。即時判定 or まとめて採点 | **事例単位で出題**。同じ絞り込みに加えて**解答の種類**（記号選択/語句/記述） |
| 本番 | 午前Ⅰ30問50分 / 午前Ⅱ25問40分 | 回と区分を選び、**4問中2問**（旧 午後Ⅰは3問中2問、午後Ⅱは2問中1問）を選択。150/90/120分 |
| 復習 | ライトナー5箱（当日 / 1日 / 3日 / 7日 / 16日、箱5正解で35日） | 同じ。ただし△は箱を動かさない |
| 年度別 / 事例別 | 回を選んで通しで | 大問を選んで、その設問を順に |

どちらも合格ラインは60%。午後は**△を0.5問**として数える。

### 午後の解き方

午後は記述式で、IPA が公開しているのは「解答例」であって正解キーではない。採点も人が
行う。だから画面は**書いたあとの瞬間**を中心に組んである。

1. 事例（10ページ前後）を読む。設問を解いている間もいつでも開き直せる
2. 空欄ごとの入力欄に書く。記述は複数行
3. `解答例と照らす` を押すと、**自分の答え・IPAの解答例・採点講評・教科書解説**が並ぶ
4. `○ / △ / ×` を自分で付ける。記号と語句は正規化して自動判定し、その結果を初期値に出す

**採点講評が効く。** 午前には無い資料で、設問ごとに正答率と典型的な誤答が書いてある
（例:「設問3(2)は，正答率が低かった。"デジタル署名"という解答が多く見られた。」）。
記述の自己採点は甘くなりがちなので、これを併記しないと箱が嘘をつく。

**△を潰さない。** 記述の「だいたい合っている」を○か×に丸めると、ライトナーの箱が
実力とずれる。○で昇格、△は同じ箱に留置、×で箱1へ戻す。

**設問から事例の該当箇所へ飛べる。** 午後の設問はほぼ必ず事例のどこかを指す
（「本文中の下線①について」「表2中の［ ］に入れる」「図4中の…を、表1中の字句を
用いて」）。8ページの散文からそれを目で探すのは骨が折れるので、設問側の参照を
押すと事例本文が開いてその位置まで送られ、1.8秒だけ光る。

| 参照 | 飛べる割合 |
|---|---|
| 図N / 表N | 463/471（98%） |
| 下線① | 386/388（99%） |
| 空欄 ［a］ | 574/631（91%） |

**設問838件のうち779件（93%）に少なくとも1つリンクが付く。** 届かない参照は
リンクにしない。押しても動かないより、素のテキストのほうがましだから。

ただし、**同じ文がその前に図表を名指ししていれば、そちらに飛ばす**。「表4中の［d］に
入れる」の ［d］ が表の中から取り出せていなくても、表4 そのものはすぐそこにあり、
読み手が見に行きたいのはどのみちそこだから。空欄574件のうち91件がこの代替。

下線そのもの（線）は図形なのでOCRには写らず、残るのは行頭の丸数字だけ。どの語句
までが下線かは復元していない。丸数字が**表の中**にあることも多いが、表は切り出した
画像に差し替えているので本文側には残らない。ただし**画像には印刷された下線がその
まま写っている**ので、画像に「隠した行が持っていた丸数字と空欄記号」を引き継がせ、
その画像へ飛ばす。

**出題は事例単位。設問はばらさない。** ライトナーの箱は設問ごとだが、**読む単位は
事例**。19回90事例から設問をランダムに引くと、設問ごとに別の10ページを開くことに
なり、しかも設問の文言は前の設問を受けていることが多いので文脈も壊れる。そこで
練習・復習とも、絞り込みで残った設問を**事例ごとにまとめ、事例の順序だけをシャッフル
する**。事例が変わるところで事例本文が自動で開き、同じ事例の中では閉じたままになる。

練習の出題数は**設問数ではなく事例数**で指定する。1事例は20〜45分の作業で、
「今日いくつ解くか」は事例の数で数えるほうが実態に合う。

**中断しても消えない。** 午後の本番は150分で、その間にアプリは必ず一度は背面に回る。
入力と採点のたびに IndexedDB に書き戻し、ホーム画面から再開できる。午前も同じ扱い。

ホームの「中断した学習」は、**解答か記入が1つでもある走行**か、**時計が動いている
本番**のときだけ出る。何もしていない走行は再開する意味がないので、記録ごと捨てる。

### 本番モードの解き方

実際の午前試験は紙のマークシートで、**制限時間内なら好きな順に解き、飛ばして戻り、
解答を書き直せる**。それに合わせてある。

- 前後どちらへも自由に移動できる（`前へ` / スワイプ）
- 未解答の数がナビゲーションバーに出る。押すと**問題番号の一覧**が開き、
  解答済み・未解答・見直し印が色で分かる。番号をタップでそこへ飛ぶ
- `☆ 見直す` で印を付けられる（CBT の「後で見直す」に相当）
- 解答は何度でも変えられる。**採点までは学習記録に書き込まない** —
  書き直すたびに1回の解答として数えると、ライトナーの箱が余計に動くため
- 時計は止まらない。一時停止はない

### 操作

- `1`〜`4` / `A`〜`D` で選択、`Enter` で次へ、`S` で解説の開閉
- `F` で見直し印、`L` で問題番号の一覧（本番・まとめて採点のとき）
- スワイプで前後の問題へ
- ダークモード（OS追従＋手動）、文字サイズ3段階

### 再出題

午前は過去問の再出題が多い。19回分で **94グループ・211問**が2回以上出題されており、
最多は5回（「衝突発見困難性」が平成28春・平成29秋・平成31春・令和3春・令和5春）。

- 出題回数を問題画面のタグに出す（`5回出題`）。その下に初出と再出題の年度を並べる
- 練習モードに「再出題された問題のみ」の絞り込みがある
- 結果画面の一覧にも回数を出すので、間違えた問題の優先順位が付けられる

本番モードでは出さない（実際の試験には無い情報のため）。

### 選択肢のシャッフル

既定でON。**解説を開くと元のア/イ/ウ/エ順に戻る** — 解説本文が「したがってウが
正解」と印刷上の記号で書かれているため。並びが動いて迷わないよう、位置が変わった
選択肢には「解答時は ウ」と併記する。

### 表・図が選択肢になっている問題

38問ある。テキストにすると意味が壊れるので選択肢ごとに画像を出す
（`choiceFigures`）。うち33問は自動で切り出せている。残り5問はマーカー位置の
推定が不確かなため画像がなく、`data/build/review.md` に載せてある。
